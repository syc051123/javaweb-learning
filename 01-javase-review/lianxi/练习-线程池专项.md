## 一、选择题（答案附解析）

### 1. 以下哪个是线程池的核心参数？

A. corePoolSize
B. maxPoolSize
C. keepAliveTime
D. 以上都是

> **答案：D**
>
> **解析：**
> 线程池有7个核心参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。
> 面试时能说出这7个就算过关。可以用餐厅的例子记：
> 2个固定厨师（core）、最多5个厨师（max）、临时工60秒没活就走（keepAlive）、排队座位（queue）、满了咋办（handler）。

### 2. 一个线程池配置：core=2, max=5, 队列=3。连续来了9个任务，第9个任务会怎样？

A. 正常执行
B. 放入队列
C. 创建新线程执行
D. 触发拒绝策略

> **答案：D**
>
> **解析：**
> 一步步推演：
> - 第1-2个任务：创建线程A、B执行（没到core）
> - 第3-5个任务：放入队列（3个位置满了）
> - 第6-8个任务：创建线程C、D、E执行（扩到max=5）
> - 第9个任务：队列已满，线程已满 → 触发拒绝策略 ❌
>
> 所以只有8个任务能正常处理，第9个被拒绝。

### 3. 以下哪个拒绝策略会直接抛异常？

A. CallerRunsPolicy
B. AbortPolicy
C. DiscardPolicy
D. DiscardOldestPolicy

> **答案：B**
>
> **解析：**
> AbortPolicy 是线程池的默认拒绝策略。队列满了、线程也满了，它就直接抛 `RejectedExecutionException`。
>
> 其他策略：
> - CallerRunsPolicy：谁交任务谁自己去干（不抛异常）
> - DiscardPolicy：悄悄丢掉（不抛异常，但任务丢了）
> - DiscardOldestPolicy：丢掉最旧的任务，给新任务腾位置

### 4. 阿里巴巴开发手册为什么禁止用 Executors 创建线程池？

A. Executors 已经废弃了
B. 因为 Executors 创建的线程池可能引发 OOM
C. 因为 Executors 性能太差
D. 手册没说原因

> **答案：B**
>
> **解析：**
> - `Executors.newFixedThreadPool(3)` 用的是无界队列 `LinkedBlockingQueue`，默认容量 **Integer.MAX_VALUE**
> - 如果任务处理不过来，队列会无限堆积，最终**内存溢出（OOM）**
>
> 正确的做法是手动 `new ThreadPoolExecutor(...)`，用有界队列（如 `ArrayBlockingQueue`），限制排队数量。

### 5. 下面哪个是 submit() 和 execute() 的区别？

A. submit() 有返回值，execute() 没有
B. execute() 有返回值，submit() 没有
C. 两者一样
D. submit() 只能提交 Callable

> **答案：A**
>
> **解析：**
> - `execute(Runnable command)`：没有返回值，不关心执行结果时用
> - `submit(Callable task)` / `submit(Runnable task)`：返回 Future 对象，可以获取结果
>
> ```java
> Future<String> future = executor.submit(() -> {
>     return "任务结果";
> });
> String result = future.get();  // 获取结果
> ```

### 6. CPU 密集型任务的线程池大小怎么设置？

A. CPU核数 + 1
B. CPU核数 × 2
C. 越大越好
D. 固定 10 个

> **答案：A**
>
> **解析：**
> CPU 密集型任务（如视频解码、加密解密）一直占用 CPU 计算。
> 线程数设太多反而不好，因为 CPU 在多个线程之间来回切换也要消耗性能（上下文切换）。
>
> IO 密集型任务（如读写数据库、调用API）大部分时间在等待，可以让线程数多一些：CPU核数 × 2。

## 二、流程推演题（这个必须会！）

### 7. 线程池配置：core=3, max=8, 队列=5。连续来了20个任务，请写出每个任务的处理方式（直接执行/排队/创建临时线程/拒绝）

> **答案：**
>
> | 任务 | 处理方式 | 原因 |
> |------|---------|------|
> | 第1-3个 | ✅ 创建核心线程执行 | 线程数 < core=3 |
> | 第4-8个 | ⏳ 放入队列 | 线程数=core，队列有5个位置 |
> | 第9-13个 | ✅ 创建临时线程执行 | 队列满了，线程数 < max=8 |
> | 第14-20个 | ❌ 拒绝 | 队列满了，线程数=max=8 |
>
> **解析：**
> 核心线程：3个（第1-3）
> 排队的：5个（第4-8）
> 临时线程：5个（第9-13，3+5=8满了）
> 被拒绝：7个（第14-20）

### 8. 接上题，如果拒绝策略是 CallerRunsPolicy，第14个任务会怎样？

> **答案：** 提交第14个任务的线程会自己执行这个任务。
>
> **解析：**
> CallerRunsPolicy 的意思是"谁提交的谁自己干"。
> 比如 main 线程提交了第14个任务，那 main 线程就会自己去执行这个任务。
>
> 这时候 main 线程被占用了，就无法继续提交第15-20个任务了。所以 CallerRunsPolicy 实际上起到了"节流"的作用——让提交者慢下来。

## 三、代码分析题

### 9. 这段代码有什么问题？

```java
ExecutorService pool = Executors.newFixedThreadPool(10);
for (int i = 0; i < 100000; i++) {
    pool.submit(() -> {
        // 模拟耗时任务
        Thread.sleep(1000);
        return "done";
    });
}
```

> **答案：** 会内存溢出（OOM）。
>
> **解析：**
> `newFixedThreadPool(10)` 的队列是无界的 `LinkedBlockingQueue`，容量是 Integer.MAX_VALUE。
> 这里提交了10万个任务，处理速度（每秒10个）远小于提交速度，所有任务都堆积在队列里。
> 10万个任务对象占用的内存会导致 OOM。
>
> **修复方案：**
> ```java
> ThreadPoolExecutor pool = new ThreadPoolExecutor(
>     10, 10, 0, TimeUnit.SECONDS,
>     new ArrayBlockingQueue<>(100),  // 有界队列，最多排100个
>     new ThreadPoolExecutor.AbortPolicy()
> );
> ```

### 10. 这段代码有什么问题？

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    2, 5, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(10),
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.AbortPolicy()
);

executor.submit(() -> doSomething());
// 没有调用 shutdown()
```

> **答案：** 没有关闭线程池，程序不会结束，线程会一直存活。
>
> **解析：**
> 线程池的核心线程默认是**一直存活**的，即使没任务可做。
> 如果程序结束了但不调用 `shutdown()`，线程池里的线程会阻止 JVM 退出。
>
> 正确做法：
> ```java
> try {
>     executor.submit(() -> doSomething());
> } finally {
>     executor.shutdown();  // 确保一定会关闭
> }
> ```

## 四、简答题

### 11. 请描述线程池处理一个新任务的完整流程

> **答案：**
>
> ```
> ① 当前线程数 < 核心线程数？
>    → 是：创建新线程执行任务
>    → 否：进入下一步
>
> ② 任务队列未满？
>    → 是：放入队列等待
>    → 否：进入下一步
>
> ③ 当前线程数 < 最大线程数？
>    → 是：创建临时线程执行任务
>    → 否：执行拒绝策略
> ```

### 12. corePoolSize 和 maximumPoolSize 为什么要设计成不一样？

> **答案：**
>
> 为了**资源利用最大化**。
> - 平时任务少：保持 core 个线程就够了，不浪费资源
> - 流量高峰：临时扩容到 max，应对突发流量
> - 高峰过去：空闲线程超过 keepAliveTime 就回收，恢复常态
>
> 就像餐厅：平时2个厨师够用，周末人多再加3个临时工，周一再辞退。
